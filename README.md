# devsecops-common-pipeline

Общий пайплайн проверок для GitHub Actions: SAST, линтеры, зависимости,
секреты, IaC, DAST. Подключается к репозиторию одной строкой `uses:`,
управляется переменными окружения.

```yaml
jobs:
  security:
    uses: dato-dev/DevSecOpsCommonPipeline/.github/workflows/security.yml@v1
```

Этого достаточно: языки определяются по файлам сборки, набор инструментов —
по языкам. Дальше всё настраивается, но ничего настраивать не обязательно.

## Установка

Пайплайн живёт в `dato-dev/DevSecOpsCommonPipeline`, образ со сканерами — в
`ghcr.io/dato-dev/devsecopscommonpipeline`. Чтобы развернуть свою копию:

1. Форкнуть или скопировать дерево, заменить `dato-dev/DevSecOpsCommonPipeline`
   на своего владельца в `.github/workflows/security.yml` (дефолт
   `scanner_image` и checkout в job `dast`), `image.yml` и `examples/*.yml`.
   Имя образа в GHCR пишется строчными буквами — регистр имени репозитория
   значения не имеет, а вот заглавные в теге образа docker не примет.
2. Поставить тег `v1.0.0` — workflow `image` соберёт и опубликует образ с
   тегами `v1.0.0`, `v1.0` и `v1`, а workflow `tags` передвинет на него
   git-теги `v1` и `v1.0`. Образ сделать публичным (Packages → Package
   settings), иначе подключённым репозиториям понадобится доступ к нему.

   Git-теги здесь не дубль тегов образа: `uses: …@v1` — это ссылка на git-ref,
   и без них подключение падает ещё до создания job'ов, с сообщением про
   «workflow file issue», в котором не сказано ничего о причине.
3. В проверяемом репозитории положить `examples/caller.yml` как
   `.github/workflows/security.yml`. Права в нём перечислены не для полноты:
   блок `permissions` заменяет набор по умолчанию целиком, и права вызванного
   workflow не могут превышать права вызывающего. Без `actions: read` сборка
   артефактов в job `report` падает с «(403) Forbidden» на своих же артефактах.

## Устройство

Логика живёт в POSIX-скриптах `ci/`, workflow — тонкая обёртка над ними.
Поэтому весь пайплайн запускается на ноутбуке:

```bash
sh ci/plan.sh          # что будет запущено и почему остальное — нет
sh ci/run.sh bandit    # один инструмент, отчёты в ./reports/
sh ci/gate.sh          # превышен ли порог
sh ci/summary.sh       # та же сводка, что уедет в PR
```

Это не удобство ради удобства. Пайплайн, который отлаживается только пушем в
CI, обрастает коммитами «fix ci» и в итоге живёт в состоянии «работает, не
трогай», а любая правка становится рискованной.

```
registry.tsv      реестр инструментов — единственное место с их описанием
versions.env      версии — их читает и Dockerfile, и локальный запуск
Dockerfile        образ со всеми сканерами
ci/plan.sh        env + автодетект -> список инструментов и матрица job'ов
ci/run.sh         запуск одного инструмента -> три отчёта
ci/tools/*.sh     по файлу на инструмент: как запустить, как разобрать вывод
ci/gate.sh        решение о падении сборки
ci/summary.sh     markdown для Summary и PR
ci/dd-push.sh     заливка в DefectDojo
```

### Отчёты

На каждый инструмент три файла в `reports/`:

| файл | зачем |
|---|---|
| `<tool>.json` | нативный вывод — его понимает парсер DefectDojo |
| `<tool>.norm.json` | общая схема — по ней считаются пороги и сводка |
| `<tool>.sarif` | GitHub Code Scanning |

Общая схема — то, ради чего всё держится вместе. `high` у bandit, `HIGH` у
trivy и `error` у ruff несравнимы между собой, а порог падения сборки должен
быть один на весь прогон. Приведение делает `tool_norm` в файле инструмента.

### Добавить инструмент

Строка в `registry.tsv` и файл `ci/tools/<tool>.sh` с двумя функциями:

```sh
tool_run()  { ... }   # запустить, записать "$OUT_JSON"
tool_norm() { ... }   # jq-фильтр: "$OUT_JSON" -> общая схема в stdout
```

Больше нигде ничего править не нужно: ни в workflow, ни в подключённых
репозиториях. Инструмент сам появится в плане там, где для него есть язык.

## Настройки

Порядок разрешения: **input вызова → переменная репозитория → автодетект →
дефолт**. Переменные (Settings → Secrets and variables → Actions → Variables)
позволяют менять набор проверок без коммита — существенно, когда пайплайн
подключён к трём десяткам репозиториев.

| Переменная | Вход `with:` | Значение | Дефолт |
|---|---|---|---|
| `SEC_LANGS` | `langs` | `auto` или `python go` | `auto` |
| `SEC_SAST` | `sast` | `1`/`0` | `1` |
| `SEC_LINT` | `lint` | | `1` |
| `SEC_SECRETS` | `secrets_scan` | | `1` |
| `SEC_DEPS` | `deps` | | `1` |
| `SEC_IAC` | `iac` | | `1` |
| `SEC_CONTAINER` | `container` | | `1` |
| `SEC_SBOM` | `sbom` | | `1` |
| `SEC_DAST` | `dast` | | `0` |
| `SEC_SAST_TOOLS` | `sast_tools` | `auto` или `bandit semgrep` | `auto` |
| `SEC_SKIP_TOOLS` | `skip_tools` | чёрный список | пусто |
| `SEC_FAIL_ON` | `fail_on` | `critical`…`low`, `none` | `high` |
| `SEC_LINT_FAIL_ON` | `lint_fail_on` | порог на категорию | `none` |
| `SEC_DAST_TARGET` | `dast_target` | URL приложения | пусто |
| `SEC_PYTHON_PATHS` | `python_paths` | что сканировать | `.` |
| `SEC_DD` | `dd` | заливать в DefectDojo | `0` |
| `SEC_<TOOL>_ARGS` | — | флаги конкретному инструменту | пусто |

`SEC_<CATEGORY>_FAIL_ON` переопределяет порог для одной категории.

Почему `SEC_LINT_FAIL_ON=none` по умолчанию: линтер на чужом проекте даёт
сотни срабатываний в первый же день, и красная сборка, которую нельзя починить
за один заход, заканчивается всегда одинаково — правило снимают целиком. Пусть
находки видно в сводке, а порог включат осознанно.

### Подавление

Файл `.security-ignore` в проверяемом репозитории:

```
# CVE в базовом образе, чинить нечем до обновления upstream
trivy-fs: CVE-2023-45853
ruff: *
```

Подавляется только влияние на порог. Находка остаётся в отчёте, в SARIF и в
DefectDojo: список исключений — это «мы решили с этим жить», а не «этого нет».

## Инструменты

| | категория | языки |
|---|---|---|
| bandit | sast | python |
| semgrep | sast | любые |
| ruff | lint | python |
| osv-scanner | deps | любые (манифесты и lock-файлы) |
| trivy fs | deps | любые (+ секреты, мисконфиги) |
| gitleaks | secrets | любые (история git) |
| checkov | iac | terraform, k8s, helm, compose |
| hadolint | container | Dockerfile |
| trivy (cyclonedx) | sbom | любые |
| pip-audit | deps | python, **не по умолчанию** |
| OWASP ZAP | dast | любые |

Первая версия закрывает Python. Go, JS и Java добавляются строкой в реестр —
см. «Добавить инструмент»; osv-scanner и trivy их поймут и так, по lock-файлам.

Колонка `default` в реестре: `0` означает, что инструмент берётся, только если
назван явно в `SEC_<CATEGORY>_TOOLS`. У pip-audit стоит ноль не из-за качества
находок, а потому что он поднимает venv и делает `pip install --dry-run`, чтобы
составить список пакетов, — и на репозитории со старыми пинами падает ровно там,
где нужен больше всего: у `cryptography==3.2` нет колеса под свежий Python, pip
уходит собирать её из исходников и не может. Режим `--no-deps` не спасает, venv
поднимается всё равно. osv-scanner разбирает манифесты статически и этой
проблемы не имеет. Вернуть pip-audit:
`SEC_DEPS_TOOLS="osv-scanner trivy-fs pip-audit"`.

## Куда уходят находки

Три приёмника, независимые друг от друга:

* **GitHub Code Scanning** — SARIF, аннотации прямо в диффе PR. На приватных
  репозиториях без GHAS шаг отвечает 403; он помечен `continue-on-error`,
  прогон из-за этого не падает.
* **Комментарий в PR** — сводная таблица и находки medium и выше. Комментарий
  один на PR и переписывается: двадцать комментариев от бота под одним PR
  читать никто не станет.
* **DefectDojo** — история находок, дедупликация, триаж. Включается `SEC_DD=1`
  и `secrets.DD_TOKEN`. Уезжает не всё: в колонке `dd_scan_type` прочерк значит,
  что парсера у DefectDojo для этого инструмента нет (ruff), и отчёт остаётся
  в артефактах и в Code Scanning. У osv-scanner прочерк стоит осторожности ради:
  в свежих версиях DefectDojo парсер `OSV Scan` есть — поставьте его в реестр,
  если ваша версия его знает. Неизвестное имя парсера даёт HTTP 400, и
  `dd-push.sh` печатает ответ целиком.

DefectDojo за самоподписанным сертификатом: положите PEM своего корневого в
`secrets.DD_CA_CERT` и пробросьте его в вызове — секреты в reusable workflow не
наследуются, каждый передаётся явно. Проверка сертификата при этом остаётся.
`DD_INSECURE=1` тоже работает, но снимает проверку целиком, и токен уходит в
соединение, подлинность которого никто не подтверждает; заданный CA сильнее.

Любая переменная репозитория с префиксом `DD_` доезжает до `ci/dd-push.sh` как
есть: `DD_PRODUCT`, `DD_MIN_SEVERITY`, `DD_ENGAGEMENT_SAST` и прочие.

Заливка в DefectDojo идёт и на красной сборке тоже: DefectDojo — это история,
а не светофор, и пропустить именно тот прогон, где что-то нашлось, было бы
странно. Используется `reimport-scan`, а не `import-scan`: import создаёт новый
Test на каждый запуск, и через месяц в engagement тридцать тестов с одними и
теми же CVE, а «когда уязвимость появилась» посчитать уже нельзя.

Engagement — по категории (`sast`, `deps`, `secrets`, …). Это не косметика:
`close_old_findings` закрывает в engagement всё, чего нет в новом отчёте, и
один общий engagement означал бы, что заливка bandit закрывает находки trivy
как «исчезнувшие».

## Образ

Все сканеры лежат в одном образе `ghcr.io/dato-dev/devsecopscommonpipeline`, job'ы
идут в нём. Версии закреплены в `versions.env` — состав находок зависит от
версии сканера, и плавающая версия даёт скачок в дашборде на ровном месте,
который потом разбирают как настоящий регресс.

```bash
sh ci/bump.sh           # показать, что устарело
sh ci/bump.sh --write   # обновить versions.env
```

Обновление — отдельный коммит, а не автоматика в сборке: изменение состава
находок должно быть видно в истории.

Тег образа совпадает с тегом пайплайна. Подключённые репозитории живут на `v1`
и получают обновления сканеров, не меняя у себя ни строки.

### Чего в образе нет

**ZAP** — это JVM и полсотни аддонов, около гигабайта ради шага, который по
умолчанию выключен. DAST идёт отдельным job'ом на самом раннере и запускает
ZAP контейнером.

**База уязвимостей trivy** — ещё под гигабайт, и устаревает быстрее, чем
пересобирается образ. Trivy скачивает её сам, в Actions её кэширует
`actions/cache`.

## Локальный запуск

Без образа скрипты работают тоже: Python-инструменты запускаются через `uvx` с
теми же закреплёнными версиями на том же Python.

```bash
export SEC_SRC=/path/to/project
sh ci/plan.sh
sh ci/run.sh bandit
sh ci/gate.sh
```

`uvx` стоит впереди `PATH` намеренно. Инструмент с `PATH` — это чужая версия на
чужом интерпретаторе: bandit разбирает код модулем `ast` того Python, на котором
запущен, и на старом интерпретаторе файл с новым синтаксисом молча уходит в
`errors`, то есть остаётся непроверенным.

## Re-run не перечитывает пайплайн

Кнопка «Re-run jobs» переиспользует SHA вызванного workflow, зафиксированный на
первой попытке: YAML остаётся тем, каким был. Тег образа `:v1` при этом
резолвится заново при старте контейнера, и скрипты внутри приезжают свежие.

Получается расхождение, которое сбивает с толку: в логе видно поведение новой
версии, а настройки, которые новая версия должна была передать в шаг, до него
не доходят — их передаёт YAML, а он старый. Чинится новым запуском: пуш или
«Run workflow», не «Re-run».

## Самопроверка

`fixtures/python-bad` — заведомо дырявый проект, на котором каждый инструмент
обязан что-то найти. `self-test.yml` гоняет его на каждом PR и раз в неделю по
расписанию и падает, если инструмент вернул ноль находок.

Проверка обратная обычной, и в этом смысл: «зелёный прогон» — это утверждение,
и оно тоже ломается. Обновился сканер, сменился формат его вывода, `tool_norm`
стал возвращать пустой массив — и пайплайн продолжает докладывать «находок
нет» на файле, где их девять. Без фикстуры это незаметно годами.

## Отвергнутые варианты

**Готовые marketplace-actions** (`aquasecurity/trivy-action`,
`zaproxy/action-baseline` и прочие) вместо своих скриптов. Меньше кода, но
версии и поведение вне контроля, локально ничего не запустить, а каждый action
приносит свой способ настройки — единого контракта из переменных не выходит.
Держим в уме для инструментов, у которых нет вменяемого CLI.

**Установка инструментов на лету** (`pip install` в шаге). Гибко и ничего не
надо публиковать, но каждый job тратит минуту на установку и ставит проверку в
зависимость от доступности PyPI в этот момент. Осталось как запасной путь для
локального запуска — через `uvx`.

**Composite action вместо reusable workflow.** Composite не умеет создавать
job'ы, то есть всё идёт последовательно в одном. На пяти сканерах это разница
между тремя минутами и пятнадцатью.
